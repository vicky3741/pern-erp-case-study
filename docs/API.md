# API Reference

Base URL (local): `http://localhost:4000/api`

Every response is JSON in one of two shapes:

```jsonc
// success
{ "success": true, "data": { /* ... */ }, "message": "optional" }
// paginated list
{ "success": true, "data": [ /* ... */ ], "meta": { "page": 1, "limit": 10, "total": 42, "totalPages": 5, "hasNextPage": true, "hasPrevPage": false } }
// failure
{ "success": false, "message": "human-readable reason", "details": { /* optional, e.g. field errors or a shortfall list */ } }
```

Authenticated routes take `Authorization: Bearer <token>`. `GET /api` (the API
root) lists every route with a one-line description and is a good starting
point in a browser or `curl`.

The full collection with chained requests covering the entire happy path and
the main failure cases lives at
[`postman/ERP-Sales-Inventory.postman_collection.json`](../postman/ERP-Sales-Inventory.postman_collection.json).

## Auth

### `POST /auth/login`
No auth required.

```jsonc
// request
{ "email": "admin@erp.local", "password": "Admin@123" }
// 200
{ "success": true, "data": { "token": "eyJ...", "user": { "id", "name", "email", "role" } } }
```

- `401` — wrong password or unknown email. **Same message either way**
  (`"Invalid email or password"`), and the comparison always runs bcrypt (even
  against a throwaway hash when the email doesn't exist), so response content
  and timing cannot be used to enumerate registered emails.
- `403` — correct credentials, but the account is deactivated.
- `400` — malformed email / missing password.

### `GET /auth/me`
Any authenticated user. Returns the caller's own profile, resolved from the
token.

### `POST /auth/logout`
Any authenticated user. A no-op server-side — JWTs are stateless — included so
there is one obvious thing for the client to call; discarding the token is
what actually ends the session.

### `GET /auth/admin-check`
`ADMIN` only. Exists purely to demonstrate that role checks are enforced by
the server: a valid `SALES` token gets `403` here regardless of what the
frontend does.

## Customers

| Method | Path | Role | Notes |
|---|---|---|---|
| GET | `/customers` | any | `?search=`, `?city=`, `?page=`, `?limit=` |
| POST | `/customers` | ADMIN, SALES | body below |
| GET | `/customers/:id` | any | detail + recent enquiries |
| PATCH | `/customers/:id` | ADMIN, SALES | partial update, same body shape |

```jsonc
// POST body
{
  "companyName": "ABC Engineering Pvt. Ltd.",
  "contactPerson": "Rajesh Kulkarni",
  "mobile": "9822012345",   // 10-digit Indian mobile, starts 6-9
  "email": "procurement@abcengineering.in",
  "city": "Pune"
}
```

- `409` — the mobile number is already used by another customer (`mobile` is
  `UNIQUE` at the database level; the message names the existing company).
- `400` — invalid mobile format, missing field, bad email.

## Enquiries

| Method | Path | Role | Notes |
|---|---|---|---|
| GET | `/enquiries` | any | `?status=`, `?customerId=`, `?search=` |
| POST | `/enquiries` | ADMIN, SALES | body below |
| GET | `/enquiries/:id` | any | detail + items + any quotations raised |
| PATCH | `/enquiries/:id/status` | ADMIN, SALES | `{ "status": "QUOTED" }` |

```jsonc
// POST body
{
  "customerId": "cmu4...",
  "enquiryDate": "2026-09-16",
  "requiredDate": "2026-10-16",
  "notes": "optional",
  "items": [
    { "productId": "cmu4...", "quantity": 100, "notes": "optional" },
    { "productId": "cmu4...", "quantity": 40 }
  ]
}
```

- `enquiryNumber` (`ENQ-YYYYMM-0001`) is generated by the server.
- `400` — no items, a product used twice in one enquiry, `requiredDate` before
  `enquiryDate`, unknown or inactive product, non-positive quantity.
- Status transitions: `NEW → QUOTED | LOST`, `QUOTED → WON | LOST`. `WON` and
  `LOST` are terminal. An illegal move returns `409` naming both the current
  status and what is allowed from it.

## Inventory

| Method | Path | Role | Notes |
|---|---|---|---|
| GET | `/inventory` | any | every product's `physicalQty` / `reservedQty` / `availableQty` |
| GET | `/inventory/:productId` | any | one product |
| PATCH | `/inventory/:productId` | ADMIN | adjust physical stock |

```jsonc
// PATCH body — exactly ONE of physicalQty or delta
{ "physicalQty": 250, "reason": "Cycle count correction" }
// or
{ "delta": 50, "reason": "Goods received against PO-1122" }
```

- `409` — the resulting `physicalQty` would go negative, or would fall below
  `reservedQty` (you cannot un-promise stock that is already reserved by
  reducing physical below it). The write is a single conditional `UPDATE`
  whose `WHERE` clause carries the guard — not read-check-write — so the row
  cannot change between the check and the write.
- `400` — both `physicalQty` and `delta` supplied, or neither, or `delta: 0`.

`availableQty` is always `physicalQty - reservedQty`; it is never stored or
accepted as input.

## Quotations

| Method | Path | Role | Notes |
|---|---|---|---|
| GET | `/quotations` | any | `?status=`, `?enquiryId=`, `?customerId=`, `?search=` |
| POST | `/quotations` | ADMIN, SALES | body below |
| GET | `/quotations/:id` | any | detail with priced line items |
| PATCH | `/quotations/:id/status` | ADMIN, SALES | `{ "status": "SENT" }` |
| POST | `/quotations/:id/convert` | ADMIN, SALES | → creates a sales order |

```jsonc
// POST body
{
  "enquiryId": "cmu4...",
  "validUntil": "2026-10-16",
  "items": [
    {
      "productId": "cmu4...",
      "quantity": 100,
      "unitPrice": 250,          // optional — defaults to the product's basePrice
      "discountPercent": 10,     // optional, default 0
      "gstPercent": 18           // optional, default 0
    }
  ]
}
```

**Every amount in the response — `lineAmount` on each item, and
`subTotal`/`totalDiscount`/`totalGst`/`grandTotal` on the header — is computed
by the server.** The request schema does not declare those fields; posting
them anyway has no effect (they never reach the service). `customerId` is
taken from the enquiry, never from the request body.

Per line:
```
base     = quantity × unitPrice
discount = base × discountPercent / 100
taxable  = base − discount
gst      = taxable × gstPercent / 100
line     = taxable + gst
```

- `400` — enquiry not found, enquiry already `WON`/`LOST`, unknown/inactive
  product, duplicate product line, discount or GST outside 0–100.
- Status transitions: `DRAFT → SENT`, `SENT → ACCEPTED | REJECTED`. `ACCEPTED`
  and `REJECTED` are terminal. Accepting an expired quotation (`validUntil` in
  the past) returns `409`. Accepting a quotation moves its enquiry
  `QUOTED → WON` in the same transaction.
- `POST /convert` — `409` unless status is exactly `ACCEPTED`; `409` if this
  quotation has already been converted (the message names the existing order
  number). See the README's "How the business rules are enforced" §2 for why
  this is guaranteed by a database constraint, not just this check.

## Sales Orders

| Method | Path | Role | Notes |
|---|---|---|---|
| GET | `/sales-orders` | any | `?status=`, `?customerId=`, `?search=` |
| GET | `/sales-orders/:id` | any | each line carries ordered / dispatched / live stock |
| POST | `/sales-orders/:id/confirm` | **ADMIN** | reserves inventory |
| POST | `/sales-orders/:id/cancel` | **ADMIN** | `{ "reason": "..." }` |
| POST | `/sales-orders/:id/dispatch` | **ADMIN** | body below |

`POST /confirm` — `409` unless status is `PENDING`. On success, `reservedQty`
rises by each line's quantity; `physicalQty` is untouched. On failure (not
enough available stock), **nothing is reserved** — the whole confirmation is
one transaction — and the response lists every short line, not just the
first:

```jsonc
// 409
{
  "success": false,
  "message": "Insufficient stock: BRG-6204 needs 80 NOS, only 70 available (short by 10)",
  "details": {
    "insufficientStock": [
      { "productId": "...", "productCode": "BRG-6204", "productName": "...", "unit": "NOS", "required": 80, "available": 70, "shortBy": 10 }
    ]
  }
}
```

`POST /cancel` — `409` if already `CANCELLED` or fully `DISPATCHED`. A
`PENDING` order has nothing reserved, so cancelling it is a status change
only; a `CONFIRMED` order releases whatever is still reserved
(`quantity - dispatchedQty` per line, so a partially dispatched order gives
back only the undispatched remainder).

`POST /dispatch` body:
```jsonc
{
  "dispatchDate": "2026-09-16",   // optional, defaults to today
  "vehicleNumber": "MH12AB1234",
  "driverName": "Suresh Patil",
  "items": [ { "productId": "cmu4...", "quantity": 60 } ]
}
```

- `409` — order is not `CONFIRMED` (message says why: never confirmed,
  cancelled, or already fully dispatched); any line requests more than
  `quantity - dispatchedQty` remaining.
- On success, `physicalQty` **and** `reservedQty` both fall by the dispatched
  quantity, per line. The order becomes `DISPATCHED` once every line's
  `dispatchedQty` equals its `quantity`; otherwise it stays `CONFIRMED`,
  allowing a further dispatch against the remainder.

| GET | `/dispatches` | any | `?salesOrderId=`, `?search=` |
| GET | `/dispatches/:id` | any | detail with its lines |

there is no standalone create route, since a dispatch only ever exists

## Error status codes, summarised

| Status | Meaning here |
|---|---|
| 400 | Validation failure (Zod) — malformed input, illegal combination of fields |
| 401 | Missing, malformed or expired token; wrong login credentials |
| 403 | Valid token, but the role does not permit this action; or the account is deactivated |
| 404 | The referenced resource does not exist |
| 409 | The request is well-formed but conflicts with the current state — illegal status transition, insufficient stock, duplicate conversion, duplicate unique field |
| 500 | Unexpected server error |
